Only two of these were open questions when the epic started. The router and the API framework were already settled in the E-LAM-0000 research documents — the tickets just had not been told.

Conventions now in force

  • Thin handlers. A handler parses a request and formats a response; anything that queries Postgres belongs in internal/document/ or a sibling.
  • Shared or feature. A component used by more than one feature, or with no domain knowledge, is shared; anything else stays in its feature.
  • Generated files are committed. api/openapi.json, schema.d.ts, and routeTree.gen.ts are all in git, and CI regenerates and diffs the first two.
  • Both CIs fail on drift. A handler change without a regeneration, or a spec pulled without regenerating types, is a red build rather than a runtime surprise.
  • New files carry OMLR comment boxes. Adopted in LAM-7; existing files are deliberately not backfilled.

Deferred

Flagged in an instruction doc, not quietly skipped — and none has a ticket

Seven open items

  1. The design system. Base UI plus Tailwind, with shadcn as a scaffold. LAM-9 shipped one unstyled Button to prove the folder, not to start a library.
  2. Enforced import boundaries. The one-way rule is documented and unenforced; React has no compile-time module boundary.
  3. End-to-end against the real stack. Playwright boots npm run dev, not the Go binary.
  4. The optimistic-write integration test. Testing Strategy §2 chose a real backend against a disposable database. That flow does not exist yet.
  5. MSW, for 401-mid-flight, 422 field errors, and network failure.
  6. oasdiff as a breaking-change gate, and TanStack Query wrappers — both need a second consumer or real server state first.
  7. openapi-typescript as a devDependency. Every published version pins typescript@^5.x and this repo is on 6.0.3, so the generator runs through npx.

The one that will bite first

The design system is the item worth filing today. The next frontend ticket that builds real UI will pick a styling approach whether or not anyone decides one, and that choice is expensive to reverse once components exist.

The rest are safe to sit. Each is written into a ticket's instruction doc with the reasoning intact, so nothing has to be reconstructed later.

Item 7 is a live constraint, not a preference: npm i -D openapi-typescript fails outright on this repo with ERESOLVE until the tool supports TypeScript 6.
